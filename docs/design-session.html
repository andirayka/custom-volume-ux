Round 3 — Settled
✓ Q11
How should we suppress the Android system volume HUD?
react-native-volume-manager can change the real volume, but Android will still show its own volume popup by default. We need to hide that so only our bar shows. The library has a flag for this, but we need to confirm the approach — does the library handle it natively, or do we need extra config?
➡️ Recommendation Use the library's built-in showSystemVolume flag — set it to false so the system HUD stays hidden while the library still fires our volume-change events. Cleanest path, no extra native code.
✓ Q12
What controls the bar's state?
The bar has two things to track: the current volume level (for the fill width) and whether it's currently visible (for the animation). These can live together in one piece of state or be split. The choice affects how clean the component stays.
➡️ Recommendation A single useState object with { level: number, visible: boolean }. Both values always change together on a press, so splitting them adds complexity without benefit. Keep it in the screen component that owns the bar.
✓ Q13
What happens when volume hits 0 or max?
When the user keeps pressing up at max volume (or down at zero), the system stops firing change events — but they're still pressing. Should the bar keep showing a subtle "at limit" state (like a brief shake or a held pulse), or just freeze at the edge and fade normally?
➡️ Recommendation Freeze at the edge, fade normally. No extra shake or indicator — it overcomplicates the demo. The bar fills to 100% or empties to 0% and behaves the same as any other level. If they press further, nothing changes; the timer still runs and it fades out.
✓ Q14
Should the bar show the volume number (like "7/15")?
Right now it's a pure visual bar. We could add a small text label showing the current level or percentage. This makes it more informative but also more "demo UI" — it might feel less like a real product feature and more like a debug overlay.
➡️ Recommendation No number label. A plain bar is cleaner and closer to what Instagram actually does. The fill position alone communicates the level. Adding text would make it feel like a debug tool, not a polished UX.
✓ Q15
Component structure — one component or split?
We need a bar component, but we also need the volume-listening logic. We could put everything in one VolumeBar component (listener + animation + render), or split into a useVolumeListener hook that returns state, and a pure VolumeBar that renders it. The split is more testable and reusable; the single component is simpler.
➡️ Recommendation Split: useVolumeListener hook + VolumeBar component. The hook owns the subscription to volume changes and returns { level, visible }. The component is purely presentational. This keeps the native wiring isolated from the animation logic and makes both easier to reason about.
